# 故障排除

某项功能出现异常、未按预期运行。本页面汇总了实际使用中遇到过的各类故障，深入分析了背后的成因以及对应的调整方法。

这里有三篇同级文档，请根据你的需求选择查阅：

- **本页面**解答*“功能出现异常/报错”*的问题，例如模型无法加载、运行意外终止、触发器从未触发等。
- [`faq.md`](faq.md) 解答*“能否支持、是否具备、位置在哪里”*的问题，例如某项特性是否受支持，以及在哪里可以找到它。
- [`user-guide.md`](user-guide.md) 详细介绍了各个界面与功能的运作机制，是行为规范的权威说明文档。另外两篇文档均通过链接引用它，而不会重复罗列相同内容。

## 模型加载失败并提示“内存不足（out of memory）”

本地大模型需要占用大块连续内存。如果加载模型失败：

- 打开“模型”页面，在更小的模型上点按“激活”。4 位量化（4-bit-quantised）变体通常能适应全精度模型无法容纳的内存空间。
- 如果你的设备上存储了多个模型，之前处于活动状态的模型会一直驻留在内存中，直到新模型被激活。在多个模型之间来回切换可能导致系统内存碎片化，彻底关闭应用（从最近任务列表中划掉）并重新打开，能够可靠地释放底层句柄。
- 请确保后台没有运行其他消耗资源的大型应用。

<!-- en: inference-is-very-slow -->
## 推理速度非常慢

在没有可用 GPU 的情况下，本地模型仅能在 CPU 上运行，这会导致生成速度明显变慢（尤其是生成前几个 token 时）：

- 在模型生成回复期间，智能体状态栏会明确标出模型实际运行的推理后端。如果配置中选择了 **GPU** 但状态栏显示为 CPU，说明 GPU 启动失败，本次会话已自动回退至 CPU。
- 位于“设置 → 模型”中的“测试后端”可以实测所选后端的生成速度。
- 尝试在“模型”页面选择更小体积的模型，在 CPU 上运行时，即使是 1B 到 2B 参数的模型，其速度也会显著快于 7B 以上的模型。
- 在“设置 → 生成 → 高级”中调低“最大上下文长度”。更短的上下文意味着每个 token 计算所需的工作量更少。

<!-- en: the-app-freezes-while-the-model-is-answering -->
## 模型回答时应用无响应/卡死

在某些手机上，当本地模型使用 **GPU** 生成回复时，屏幕可能会暂时失去响应，Android 系统甚至可能弹出应用无响应、建议关闭的提示。这是因为模型与屏幕显示共享同一个图形芯片，模型长时间高度占用 GPU 会导致界面渲染被迫等待。设备端推理引擎虽已规划了旨在保持屏幕流畅的低优先级调度模式，但目前第三方应用尚无法通过公开接口开启该模式（参见 [LiteRT-LM#3992](https://github.com/google-ai-edge/LiteRT-LM/issues/3992)）。

在该问题彻底修复前，可打开“设置 → 模型”，将“推理后端”更改为 **CPU**，并点按提示横幅上的“重启”。这样回答生成速度会有所下降，但界面将不再受制于模型计算而卡死。

<!-- en: a-tool-says-it-is-unavailable -->
## 工具提示不可用

常见原因有两种：

- 某些将任务委托给云端服务商的内置工具（例如 **delegate_task**），要求必须在“设置 → 模型 → 外部服务商”中配置至少一个云端 API 密钥。若没有可用密钥，该工具会对智能体自动隐藏。
- MCP 服务器工具要求服务器本身处于可连接状态。请打开“工具”页面，确认该服务器仍列在“MCP 服务器”下方；如果服务器 URL 发生变更或服务器停机，调用该工具时会在控制台中报错。

<!-- en: an-mcp-server-is-connected-but-a-tool-i-expect-isnt-there -->
## 已连接 MCP 服务器，但期望的工具未显示

如果服务器行状态显示为 `ok` 但该工具始终未列出，通常是由于服务器并未向本应用发布该工具。某些工具依赖客户端提供 Knotwork 暂未支持的扩展特性，行为规范的服务器会直接从列表中省略这些工具，而不是提供一个调用必然失败的接口。详见[服务器行上工具数量的含义](user-guide.md#what-the-tool-count-on-a-server-row-means)：这是客观的功能局限，并非可以在“工具”页面排查修复的配置错误。

如果该工具在服务器下方列出，但被标记为*不向智能体提供*，说明存在同名工具冲突：可能是设备上的本地工具，或者是列表中更靠前服务器上的相同工具。详见[两个工具同名时的处理](user-guide.md#when-two-tools-share-a-name)。

<!-- en: the-same-question-goes-to-the-cloud-one-time-and-stays-local-the-next -->
## 相同的问题有时发送到云端，有时留在本地处理

这通常是意图路由器结合上下文会话进行判断的结果，并非程序缺陷。如果希望分流决策始终保持一致可复现，请参阅[为什么相同的问题可能走不同的路由路径](user-guide.md#why-the-same-question-can-take-a-different-route)了解具体的调整方法。

<!-- en: a-background-run-dies-the-moment-i-leave-the-app -->
## 离开应用瞬间后台运行立即终止

这几乎总是由于系统的电池优化策略导致的，而非应用自身的缺陷：在系统默认设置下，切出应用后数秒之内进程就可能被系统直接回收。详见[电池设置决定了后台任务能否执行](user-guide.md#battery-settings-decide-whether-any-of-this-happens)。绝大多数从未产出结果的触发器和计划任务，根源均在于此。

<!-- en: a-pipeline-went-missing -->
## 流程丢失

如果你删除或重命名了某个聊天当前绑定的流程，在该聊天发送下一条消息时，将自动回退到流程库中标记为**默认**的流程。这不会导致应用报错崩溃，回复功能依然正常，只是对话会开始使用当前被标记为默认的流程。若要重新为该聊天指定流程，可以重新打开“流程”页面并使用“设为默认”，或者新建一个聊天以重新绑定。

<!-- en: the-agent-stopped-mid-run -->
## 智能体在中途停止运行

长时间执行的复杂运行可能会达到设置的某项**运行限制**。此时运行会进入暂停状态并询问处理方式：聊天界面会提示**因达到安全限制而暂停**，说明哪项配额已耗尽以及具体消耗了多少，并提供“继续（+N）”或“停止运行”两个选项。选择继续将为其追加一份相同的配额并从中断处继续推进；当这段追加配额再次耗尽时会重新询问。

如果运行直接停止而没有暂停，聊天界面会提示**因达到安全限制而停止**：这说明你主动选择了停止、等待窗口在你回复前已超时关闭，或者该运行没有可挂起的持久化记录（例如来自编辑器的测试运行）。在该消息上点按“调整限制”可以打开配置页面，提高下次运行的配额上限。

在提高限制之前，有两点值得注意：涉及的限制可能是 **token** 额度而非步数限制，因此请仔细阅读提示文本，不要盲目猜测；此外，非你手动启动的运行受**后台**限制规则约束，该项配额在同一设置界面中单独配置。

但请务必先仔细查看提示消息，因为并非所有中途停止都源自限制触发。**已停止：运行毫无进展**意味着运行陷入了死循环重复，因此被系统强制终止：此时盲目提高限制只会让它多空转几圈，请打开控制台查看究竟是哪个步骤在不断重复。**已停止：运行无响应**则是第三种情况：某个步骤停止响应，通常是外部工具或服务器始终未返回数据，系统终止该运行以便让其他消息得以执行。这种情况在第二次重试时往往可以恢复正常。

<!-- en: a-trigger-didnt-fire -->
## 触发器没有触发

打开该触发器并查看其**评估日志**（详见[触发器](user-guide.md#checking-what-a-trigger-has-been-doing)），答案几乎都在其中，其表现形式通常分为以下三种，分别对应着不同的后续操作：

- **在你预期的时刻存在记录，但显示未执行。** 日志中会明确注明原因：条件不满足、在该时间窗口内此前已经触发过、触发器处于关闭状态，或是未绑定任何流程。功能本身运转正常：要么是实际触发条件与你的预期有出入，要么是该触发器尚未绑定流程或未开启。
- **存在记录且已触发，但执行结果异常。** 标记为“失败”表明问题出在流程内部（打开该触发器对应聊天中的具体运行并查阅控制台）。其中两类故障带有自我诊断信息：*运行毫无进展*说明陷入了死循环，控制台日志会显示同一步骤在终止提示前被反复执行；*运行无响应*表明某个步骤停滞，控制台日志末尾会停留在已启动但从未完成的那个步骤上，该步骤就是排查的核心，不过“变量”标签页中该步骤不会有任何输出，因为它从未执行完成；*已被系统停止*意味着进程在执行中途被系统杀掉，属于电池策略或内存压力问题，而非流程逻辑缺陷；*等待批准超时*意味着运行暂停等待敏感工具授权，但审批窗口在你响应前已过期：你可以更快地做出审批、在“设置 → 后台与触发器 → 审批时间窗口”中延长等待时间，或者改用工具无需批准的流程。如果日志记录提示*请求从未送达给你*，说明发生了相反的情况：审批通知根本无法交由系统弹出，因此不值得继续等待。
- **在预期的时刻前后完全没有任何记录，** 且列表中标记为**已逾期**。这说明系统根本没有唤醒应用进行检查。这是操作系统层面的限制问题：请将应用加入电池优化白名单；在带有厂商额外后台控制层（如三星、小米、一加等）的手机上，还需将其移出任何“睡眠应用”或“深度睡眠”列表中。请注意，除“充电中”以外的所有触发器都基于系统可延迟的后台调度机制运行（详见[触发器多快能触发](user-guide.md#how-soon-a-trigger-fires)），偶发的检查延迟属于正常现象，但如果间隔达到了触发器自身周期的数倍，则属异常。

从未进行过任何评估的全新触发器会显示*“暂无评估记录”*：刚创建时显示此状态完全正常，因为首次检查需要等待下一个轮询周期的到来。

## 记忆搜索未能找到明显存在的条目

如果你确信存在的某条记忆从未在回答中被引用（或未在“记忆”页面的搜索中出现），请按以下列表逐项排查：

- **节点未配置读取记忆。** 只有开启了**长期记忆**输入标志的节点才会从记忆库中拉取信息。请打开对应流程，检查节点的“输入数据”设置，并观察“控制台 → 记忆”筛选视图：如果该次运行没有打印 `Memory: query=… → N hits` 日志行，说明当前节点从未查询过记忆库。
- **相似度阈值设置过高。** 若在“设置 → 记忆 → 相似度阈值”中设定了过高的数值，弱相关的记忆分片在进入提示词前就会被过滤抛弃。可尝试调低该阈值（或将该条目置顶：置顶的分片将完全绕过阈值过滤，并始终排在最前面）。
- **较新的条目抢占了配额槽位。** 保存时间本身绝不会导致条目被剔除（只要分片能够通过相似度阈值过滤，无论存了多久都保持可检索状态），但在相关度接近时新鲜度是决定排名的平衡因子：当通过阈值筛选的条目数量超过了“搜索结果数（Top-K）”的配额限制时，较新的记忆会优先抢占槽位。可尝试调高 Top-K、调大“时效半衰期”（这能放宽判定新旧权重的时间窗口），或者直接置顶该条目。
- **存在表达相同含义的其他条目。** 如果某条记忆的语义与另一条排名更高的条目高度重合，系统会将其合并折叠，避免用措辞相似的重复记录占用宝贵的上下文槽位。如果存在置顶条目，保留下来的必然是置顶副本，否则保留排名最高的副本；在相关度与时间大致持平的情况下，你手动保存的记忆优先级高于系统自动提取的记忆。在采用设备端嵌入模型时，这一规则还会将俄语书写的无关联条目判定为重复（模型无法有效区分它们），详见[已知局限](faq.md#known-limitations)。
- **该条目正在排队等待重新嵌入。** 在不同嵌入模型服务商之间迁移导入的分片，在后台重新嵌入完成之前无法被匹配命中（在此期间其匹配得分约为 0）。请稍候片刻，或前往“设置 → 记忆 → 重新嵌入”强制立即执行。
- **更改了嵌入模型服务商。** 切换“嵌入模型”会导致已有的分片仍保留在旧的向量空间中；请执行“重新嵌入”，使整个记忆库重新统一至当前活动服务商的向量空间。在模型不匹配期间，“记忆”卡片上会常驻显示*建议重新嵌入*的提示横幅。
- **开启了“禁止本地模型访问网络”。** 开启该设置后，记忆库将无法使用 OpenAI 作为“嵌入模型”，也无法连接非 `localhost` 或非专用 IP 的 Ollama 服务器，系统会自动回退至设备端模型：这会导致由另一服务商嵌入的条目得分归零，直到你关闭该网络限制。该限制同时还会屏蔽内置的 `search_tool`，导致原本通过 Wikipedia 查询事实的步骤直接报错拒绝并指明该设置项，而无法返回提取内容。
- **该信息从未被系统提取为记忆。** 自动提取机制仅会保留长期事实（如偏好、重要事件、人际关系），并自动跳过闲聊客套以及已有事实。如果你已具备某项事实，新信息的到来会直接更新现有条目，而不会重复新建；对于置顶条目，新信息会在其旁边等待更新。如果某个关键事实未被系统自动捕捉，可使用“保存到记忆”或点按“添加记忆”悬浮按钮手动补充。

## 启动时显示“无法解锁你的数据”

所有本地数据均存储在加密数据库中，其加密密钥受 Android 硬件安全密钥库（Keystore）保护。在极少数特殊情况下（通常是在系统升级后，或由于底层 Keystore 发生瞬时故障），该密钥可能暂时变为不可读状态，此时应用在启动时会展示专门的恢复界面：

- **首先尝试点按“重试”，可多次尝试。** Keystore 故障往往是暂时性的；只要密钥恢复可读，应用就能完好无损地打开并加载你现有的全部数据。在再次重试之前重启手机在某些情况下也会有所帮助。
- **“清除数据”是最后的补救手段。** 如果无论如何重试都无法通过该界面，说明密钥已彻底丢失损坏，加密数据库已无法被任何人打开（包括应用自身）。点按“清除数据”会删除本地数据库、智能体工作区文件、附件以及计划任务，并重新生成一把全新的密钥以便你重新开始。设置项与已保存的密钥会被保留，已下载的模型也会保留（它们会重新列在“模型”下方处于未激活状态，在开始聊天前需重新激活其一）。该操作不可撤销，且受输入确认机制保护。

在这种状态下，应用绝不会擅自自动删除或重新生成数据密钥：失去原始密钥就意味着数据库内容无法复原，因此清空重建的决定权始终完全交由你掌控。

## 覆盖安装 Google Play 版本的应用失败

在已安装 Google Play 版本的设备上直接安装来自 GitHub 的 Release APK 或 F-Droid 版本的 Knotwork 时，安装会中断并提示*应用未安装*或*安装包与现有安装包存在冲突*等错误；具体文案取决于当前 Android 系统版本以及执行安装的文件管理器应用。反之亦然：从 Release APK 或 F-Droid 安装的副本无法直接通过 Google Play 覆盖更新。

安装包本身没有任何损坏。这是因为 Google Play 使用的签名密钥与 GitHub 发布版及 F-Droid 的签名密钥不同（参见[各发布渠道的签名身份说明](release.md#signing-identities-by-channel)），而 Android 系统强制要求更新安装包必须来自相同的签名主体。若要切换安装渠道，请按以下步骤操作：

1. 创建备份：前往“设置 → 隐私 → 备份与恢复 → 备份…”（详见[说明](user-guide.md#backup--restore)）。勾选“包含 API 密钥与登录信息”以保留你的密钥，并将备份文件妥善保存在卸载应用无法波及的位置，如“下载”目录、存储卡或云端网盘。
2. 卸载现有应用。该操作会删除应用在设备上保留的所有数据，包括已下载的模型。
3. 从新渠道安装应用，打开“备份与恢复 → 从文件恢复…”，选中备份文件，输入解密密码并确认。应用重启后，可在弹出的面板中重新下载所需模型。

所安装的目标版本必须具备读取该备份文件的兼容能力。较新版本的备份通常可以在旧版本中恢复，除非该版本修改了备份文件结构或底层数据库架构；此时恢复操作将被拒绝并提示你先更新应用。在应用商店审核期间，Google Play 的版本可能暂时落后于 Releases 页面，F-Droid 也需等待其构建任务完成，因此在卸载之前，请务必核实新渠道提供的安装包版本与当前版本一致或更新。

<!-- en: a-model-download-paused-after-five-hours -->
## 模型下载在 5 小时后暂停

Android 限制单个应用每天在后台传输数据的累计时长不得超过 6 小时，若传输超时系统将强制休眠该应用。因此，模型下载在连续执行 5 小时后会自动主动暂停。系统会发送一条说明暂停原因的通知（前提是已授予通知权限），且在你下次打开应用并未运行其他下载时，“模型”页面会显示带有“继续”按钮的提示卡片；若先进入初始设置的下载步骤或“发现”中的模型详情页，也会看到相同提示。已下载的数据完全不会丢失：再次启动该下载即可断点续传。

<!-- en: a-downloaded-model-did-not-match-its-checksum -->
## 下载的模型校验和不匹配

Hugging Face 会为其托管的模型文件公布 SHA-256 校验和，应用在安装模型之前会将下载的本地文件与之进行比对。如果两者不一致，文件将被删除，模型不会被安装，应用也会以与暂停下载类似的方式向你提示说明。

导致这种情况的一个常见原因是：在下载中断期间 Hugging Face 仓库更新了该模型文件，导致中断前下载的分片与中断后下载的分片实际上分别属于不同版本的文件。只需重新启动下载，应用就会从头完整下载当前最新版本的文件。

如果重新下载依然提示校验和不一致，说明传输到手机上的文件与 Hugging Face 官方发布的文件内容不符。请尝试切换其他网络环境重试；若问题依然存在，请提交 Issue 并注明对应的模型名称与文件名。
